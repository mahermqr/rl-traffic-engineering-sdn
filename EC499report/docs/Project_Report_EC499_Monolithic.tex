\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

Modern telecommunication infrastructures and cloud datacenter fabrics are constrained by non-stationary traffic dynamics, localized microbursts, and rigid routing heuristics. Traditional interior gateway protocols---predominantly Open Shortest Path First (OSPF, RFC 2328) and Equal-Cost Multi-Path (ECMP)---rely on static administrative metrics decoupled from instantaneous buffer occupancy. Under asymmetric traffic loads, these protocols persistently direct traffic along identical shortest paths, inducing core link saturation, bufferbloat, tail-drop packet loss, and packet delay variation (jitter), while viable edge-disjoint bypass paths remain underutilized.

This graduation dissertation presents the design, implementation, and evaluation of a closed-loop Adaptive Traffic Engineering (TE) prototype powered by Deep Reinforcement Learning (DRL) over an OpenFlow 1.3 Software-Defined Networking (SDN) substrate. The control plane integrates a Dueling Double Deep Q-Network (D3QN), a binary SumTree Prioritized Experience Replay (PER) engine, and a thresholded multi-objective reward. The agent consumes normalized 10-dimensional link and candidate-path features and selects among loopless candidate paths synthesized with Yen's $K$-shortest-paths algorithm, with invalid actions masked. A health-checked active/standby controller pool provides automated failover resilience, delivering an internal local role promotion bookkeeping time of $0.001$~ms and an end-to-end client HTTP recovery of $37.96$~ms under simulated primary process failure.

The evaluation benchmarks D3QN across five network topologies against both static baselines (OSPF, Dijkstra SPF, ECMP) and dynamic heuristics (Least-Loaded Routing, LLR, and Widest-Shortest Path, WSP). In the multi-topology tournament under heavy load, D3QN achieves substantial congestion relief across multipath fabrics, lowering arithmetic-mean bottleneck utilization from $66.80\%$ (OSPF) to $30.80\%$ and reducing modelled latency from $158.34$~ms to $44.50$~ms. However, the evaluation also demarcates clear operational boundaries: on rigid tree topologies with single root bottlenecks, greedy dynamic heuristics like LLR deliver comparable or superior throughput ($38.09$~Mbps vs. $34.08$~Mbps for D3QN) without neural inference overhead. Furthermore, empirical 120-trial Mininet namespace emulations reveal that dynamic multi-path switching interacts with TCP window congestion control, resulting in higher packet loss under TCP than static SPF ($36.0\%$ vs. $18.0\%$). Consequently, this work establishes that DRL-based traffic engineering is most advantageous on rich multipath fabrics with diverse edge-disjoint routing options, while deterministic heuristics remain competitive in single-bottleneck architectures.

\chapter{Introduction}
\label{chap:introduction}

\section{Problem Statement}
Modern enterprise networks, fifth-generation (5G) telecommunication cores, and hyper-scale cloud datacenter fabrics are subjected to unprecedented traffic dynamism. Traffic profiles are characterized by extreme spatiotemporal volatility, uncoordinated microbursts, and asymmetric demands driven by real-time high-definition video streaming, machine learning model synchronization, distributed database replication, and low-latency cloud gaming. 

Despite these evolving demands, contemporary network infrastructures continue to rely heavily on legacy interior gateway routing protocols designed in the late twentieth century---predominantly Open Shortest Path First (\textbf{OSPF}, RFC 2328) \cite{moy1998ospf} and Intermediate System to Intermediate System (\textbf{IS-IS}). These protocols compute packet forwarding paths using static administrative link metrics, typically configured inversely proportional to link capacity. While computationally lightweight and robust against routing loops, static shortest path routing exhibits fundamental systemic flaws:
\begin{enumerate}
    \item \textbf{Decoupling from Instantaneous Network State:} Static metrics remain completely unaware of instantaneous buffer occupancy, queueing delay, jitter, or link utilization. 
    \item \textbf{Asymmetric Core Saturation:} Under asymmetric or bursty traffic conditions, static shortest path routing persistently directs traffic along identical shortest paths, inducing severe bottleneck link saturation ($>90\%$), massive bufferbloat, tail-drop packet loss, and severe packet delay variation (jitter, RFC 3393) \cite{deroo2002ip}.
    \item \textbf{Gross Underutilization of Alternative Paths:} Simultaneously, viable edge-disjoint and loop-free bypass paths remain completely idle ($0\%$--$10\%$ load), squandering massive bisection bandwidth.
    \item \textbf{Limitations of Equal-Cost Multi-Path (ECMP):} While ECMP provides flow-level load balancing across strictly equal-cost paths, it is incapacitated when alternative paths differ by even a single administrative metric unit or hop. Furthermore, static 5-tuple hash collisions persistently assign multiple high-bandwidth ``elephant flows'' to identical links, causing hash polarization and severe congestion.
\end{enumerate}

\section{The Importance of the Experiment and Why It is Important}
Traffic Engineering (TE) is the science of optimizing network operational performance by dynamically steering traffic flows across physical network resources. In carrier-grade and cloud infrastructures, the consequences of suboptimal traffic engineering are severe:
\begin{itemize}
    \item \textbf{Strict SLA Violations:} Enterprise and carrier Service Level Agreements (SLAs) enforce stringent latency and zero-drop bounds. Even momentary buffer overflows induce TCP timeout cascades, packet retransmissions, and severe throughput collapse.
    \item \textbf{Real-Time Interactive Service Degradation:} Modern interactive applications (e.g., autonomous driving telemetry, financial high-frequency trading, tactile Internet, voice over IP) are acutely sensitive to RFC 3393 packet delay variation (jitter) \cite{deroo2002ip}. Standard heuristics optimize for hop count rather than jitter, leading to severe quality-of-service (QoS) degradation.
    \item \textbf{Capital and Operational Expenditure Waste:} Telecommunication operators invest billions in high-capacity fiber meshes. Inefficient TE forces over-provisioning of expensive core links, while available alternative capacities remain stranded.
    \item \textbf{Inadequacy of Traditional Centralized Solvers:} Prior centralized optimization platforms (such as Google B4 \cite{jain2013b4} and Microsoft SWAN \cite{hong2013achieving}) formulate TE as a centralized Multi-Commodity Flow (MCF) linear program. However, solving large-scale linear programs incurs computational latencies spanning tens of seconds to minutes, making them incapable of mitigating sub-second transient congestion and localized microbursts.
\end{itemize}

Therefore, there is an urgent scientific and operational need for an \textbf{autonomous, closed-loop, intelligent Traffic Engineering system} that can make low-latency routing decisions, adaptively balance offered flows, reduce congestion-related loss and jitter, and provide a resilient control-plane prototype.

\section{Solution Methodology and Main Steps}
To overcome the aforementioned challenges, this graduation project presents the design, mathematical formalization, software implementation, and empirical validation of an autonomous, closed-loop Adaptive Traffic Engineering platform powered by \textbf{Deep Reinforcement Learning (DRL)} over an \textbf{OpenFlow 1.3 Software-Defined Networking (SDN)} substrate.

The core solution methodology comprises five primary steps:
\begin{enumerate}
    \item \textbf{SDN-Based Closed-Loop Control Plane:} Leveraging Software-Defined Networking to decouple control intelligence from physical packet-forwarding hardware. An OpenFlow 1.3 controller application built on the Ryu framework periodically collects high-resolution port telemetry ($\Delta t = 1.0$~s) and installs flow-table modifications dynamically.
    \item \textbf{Dueling Double Deep Q-Network (D3QN) Engine:} Formulating the traffic steering decision process as a model-free Markov Decision Process (MDP). The D3QN architecture separates state-value estimation $V(s)$ from action-advantage estimation $A(s,a)$; Double-DQN target selection is used to reduce, rather than eliminate, overestimation bias.
    \item \textbf{Binary SumTree Prioritized Experience Replay (PER):} Replacing naive uniform experience replay with an optimized binary SumTree data structure, ensuring transitions with large Temporal Difference (TD) error magnitude are sampled with high priority in $O(\log N)$ time, accelerating convergence and retaining rare congestion events.
    \item \textbf{Thresholded Multi-Objective Reward Function:} Combining path hop count, delay, jitter, loss, and a quadratic congestion penalty. The implemented penalty increases after 70\% bottleneck utilization, encouraging proactive rerouting; it is a heuristic objective rather than a hard safety guarantee.
    \item \textbf{Health-Checked Active/Standby High Availability (HA) Clustering:} Implementing a 3-node distributed controller pool with HTTP health probing, local primary selection, and transparent client retry, delivering sub-millisecond local failover bookkeeping ($0.001$~ms) and $37.96$~ms client HTTP recovery under controller process termination.
\end{enumerate}

\section{Project Contributions}
This graduation project makes the following seven substantial scientific and engineering contributions:
\begin{enumerate}
    \item \textbf{D3QN Routing Engine with Action Masking:} A fully synthesized, mathematically verified Dueling Double DQN architecture specifically engineered for SDN traffic engineering, featuring normalized 10-dimensional continuous state vectors, dynamic invalid-action masking for variable candidate path counts, Layer Normalization, and Polyak target soft-updates (\code{agent/dqn_router.py}).
    \item \textbf{Binary SumTree Prioritized Experience Replay:} An optimized implementation of PER utilizing a complete binary tree data structure to achieve $O(\log N)$ priority updates and proportional transition sampling with annealed importance-sampling weight correction (\code{agent/prioritized_replay.py}).
    \item \textbf{Thresholded Multi-Objective Reward Engine:} An implemented reward formulation combining hop count, modelled queue delay, jitter, loss, and a quadratic congestion term with an additional penalty above the configured 70\% threshold.
    \item \textbf{Resilient Multi-Controller Failover Pool:} A validated active/standby multi-controller pool demonstrating an internal leader promotion bookkeeping latency of \textbf{0.001~ms} and an end-to-end client HTTP failover recovery time of \textbf{37.96~ms} under controller process failure injection (\code{controller/ha_controller_pool.py}).
    \item \textbf{Comprehensive Multi-Topology Benchmark Tournament:} A model-based routing tournament across five standard topologies (Hierarchical Tree, Fat-Tree Clos, Abilene US Backbone, NSFNet, Spine-Leaf). In the checked-in reference run, D3QN has lower arithmetic-mean bottleneck utilization, latency, jitter, and loss than OSPF; the values, aggregation method, and limitations are reported in Chapter~\ref{chap:project}. These results are simulation/emulation-model outcomes, not hardware-network measurements.
    \item \textbf{Transfer Evaluation on Tested Graph Distributions:} An exploratory evaluation of a trained agent on unvisited random graphs without fine-tuning. It is evidence on those generated workloads, not a claim of topology-invariant routing.
    \item \textbf{Implementation and Automated Verification Suite:} A modular codebase accompanied by a 42-test automated unit and integration suite (\code{test_suite.py}). Passing tests establish the covered software behavior; they do not independently validate performance claims.
\end{enumerate}

\section{Scope, Assumptions, and Operational Boundaries}
This graduation project focuses on the design, mathematical formulation, software implementation, and empirical evaluation of an autonomous traffic engineering platform operating within a virtualized Linux software-defined network environment.
The scope is characterized by the following operational boundaries:
\begin{itemize}
    \item \textbf{Software Substrate:} Evaluated using Ryu SDN Framework (OpenFlow 1.3), Open vSwitch 2.17, Mininet 2.3.0, and PyTorch 2.0+ on 64-bit Ubuntu Linux 22.04 LTS.
    \item \textbf{Forwarding Regime:} Unsplittable unicast flow forwarding. Multi-path packet-level splitting (which induces TCP packet reordering and duplicate ACKs) is excluded.
    \item \textbf{Candidate Route Cardinality:} Action spaces are bounded to $K = 4$ loopless candidate paths synthesized via Yen's algorithm, bounding inference complexity to $O(1)$.
    \item \textbf{Emulation Boundaries:} Evaluated inside kernel-level network namespaces (Mininet). Hardware ASIC testing on Barefoot Tofino or Broadcom StrataXGS is identified as future work.
\end{itemize}

\section{Hardware, Software Tools, and Key Equipment: Why Each Was Chosen}
In accordance with the Faculty of Engineering graduation project guidelines, this section presents the core equipment, software tools, and frameworks chosen to realize this project, providing a rigorous technical justification for why each tool was selected:

\begin{enumerate}
    \item \textbf{Software-Defined Networking (SDN) and OpenFlow 1.3 Protocol:}
    Traditional distributed routing architectures couple the control logic and packet forwarding hardware within individual closed vendor routers. This architectural coupling prevents global optimization and dynamic policy reconfiguration. SDN was chosen because it cleanly decouples the control plane from the data plane, providing logically centralized network visibility and dynamic software programmability. OpenFlow version 1.3 (ONF TS-006) \cite{onf2012openflow} was specifically selected because:
    \begin{itemize}
        \item It supports multi-stage pipelined Flow Tables and Group Tables.
        \item It provides standardized, high-precision per-port and per-flow byte/packet counters via \code{OFPPortStatsRequest} and \code{OFPFlowStatsRequest}.
        \item It is natively supported by modern kernel-space virtual switches (Open vSwitch) and hardware merchant silicon ASICs.
    \end{itemize}

    \item \textbf{Ryu SDN Controller Framework:}
    The control plane requires an extensible, robust, and event-driven software framework. While monolithic Java-based controllers (such as ONOS or OpenDaylight) provide carrier features, they impose massive memory footprints ($>4$~GB RAM) and high JVM warmup latency. Ryu was selected because:
    \begin{itemize}
        \item It is fully implemented in Python, allowing direct, zero-overhead in-memory integration with scientific computing and machine learning libraries (PyTorch, NumPy, NetworkX).
        \item It utilizes an asynchronous event-driven architecture based on Eventlet green threads, ensuring responsive coroutine handling of OpenFlow messages.
        \item It provides native, robust packet-parsing libraries for LLDP, IPv4, TCP, UDP, and ARP protocols.
    \end{itemize}

    \item \textbf{Mininet Network Emulation Platform:}
    To evaluate the platform under realistic conditions without requiring million-dollar physical switch hardware, an emulation environment is required. Mininet (version 2.3.0) was chosen because:
    \begin{itemize}
        \item Unlike discrete-event software simulators (e.g., NS-3 or OMNeT++), Mininet runs \textbf{real production software}: real Linux kernel network stacks, real Open vSwitch (OVS) kernel datapath modules, and real application binaries (iperf, ping, curl).
        \item It employs lightweight OS-level Linux network namespaces (\code{netns}) and virtual Ethernet (\code{veth}) pairs, enabling high-fidelity emulation of complex 20-switch, 32-host topologies on commodity x86 hardware.
        \item It supports exact, reproducible topological creation via programmatic Python scripts.
    \end{itemize}

    \item \textbf{PyTorch Deep Learning Library:}
    The reinforcement learning intelligence engine requires a high-performance deep learning framework. PyTorch 2.0+ was selected because:
    \begin{itemize}
        \item It provides dynamic computational graphs (eager execution), facilitating rapid forward-inference and transparent backpropagation.
        \item It features highly optimized C++/CUDA tensor kernels with sub-millisecond execution overhead ($0.24$~ms inference for the D3QN agent).
        \item It supports modular neural layers, custom activation functions (LeakyReLU), Layer Normalization, and advanced optimizers (Adam with gradient clipping).
    \end{itemize}

    \item \textbf{Health-Checked Active/Standby High-Availability Architecture:}
    A single centralized SDN controller represents a vulnerable single point of failure (SPOF). To provide fault tolerance and continuous control plane operation, a health-checked active/standby multi-controller pool was implemented. The pool architecture utilizes HTTP health probes to monitor node vitality, initiates sub-millisecond local failover bookkeeping ($0.001$~ms) to designate an available standby, and provides transparent client retry with automated endpoint redirection, avoiding the operational complexity of external consensus daemons while ensuring rapid controller recovery.

    \item \textbf{Programmable Data Planes (P4) and In-Band Network Telemetry (INT):}
    While OpenFlow 1.3 provides standard southbound abstractions, emerging carrier networks are transitioning toward fully programmable data planes. P4 was evaluated as the architectural target for hardware deployment, offering line-rate packet parsing, stateful on-switch register processing, and nanosecond-resolution telemetry without control-plane polling overhead.
\end{enumerate}

\section{Programmable Data Planes (P4) and In-Band Network Telemetry (INT)}
\label{sec:p4_int_background}
To understand the architectural evolution of software-defined forwarding, it is essential to contextualize OpenFlow against modern \textbf{Programmable Data Planes} driven by the \textbf{P4 (Programming Protocol-Independent Packet Processors)} language:

\begin{enumerate}
    \item \textbf{Limitations of OpenFlow's Fixed Pipeline:}
    OpenFlow 1.3 relies on a standardized, fixed-function packet parser that recognizes a hardcoded set of packet headers (Ethernet, VLAN, IPv4, IPv6, TCP, UDP, MPLS). If a telecommunication carrier introduces a novel encapsulation protocol (e.g., Segment Routing over IPv6, SRv6) or custom telemetry tags, the OpenFlow switch firmware must be completely redesigned. Furthermore, OpenFlow telemetry is fundamentally reactive and asynchronous: port and flow statistics are retrieved via periodic pull requests (\code{OFPPortStatsRequest}), introducing a minimum polling lag of $\Delta t \approx 1.0$~second.

    \item \textbf{The PISA Architecture and P4 Model:}
    The Protocol-Independent Switch Architecture (\textbf{PISA}) introduces a fully programmable packet processing pipeline comprising:
    \begin{itemize}
        \item \textbf{Programmable Parser:} Expressed as a state machine that parses arbitrary, custom-defined header sequences from bitstreams.
        \item \textbf{Ingress Match-Action Stages:} Reconfigurable lookup tables supported by Ternary Content-Addressable Memory (TCAM) and Static RAM (SRAM), accompanied by stateful Register arrays that maintain line-rate state across consecutive packets.
        \item \textbf{Queuing and Traffic Manager:} Manages packet buffer queues, packet replication (multicast), and traffic shaping.
        \item \textbf{Egress Match-Action Stages:} Applies egress modifications, encapsulations, and queuing telemetry insertions.
        \item \textbf{Programmable Deparser:} Reassembles modified headers into outgoing Ethernet bitstreams.
    \end{itemize}

    \item \textbf{In-Band Network Telemetry (INT):}
    Developed by the P4.org telemetry working group, In-Band Network Telemetry (\textbf{INT}) eliminates periodic polling overhead entirely. Instead of an external controller querying switches, transit switches embed real-time metadata directly into the payload or shim encapsulation of user data packets at hardware line rate (e.g., 400 Gbps per port on Intel Barefoot Tofino ASICs). As a packet traverses the network:
    \begin{itemize}
        \item Ingress switches insert an INT header.
        \item Each intermediate hop pushes its unique \textbf{Switch ID}, \textbf{Egress Port}, \textbf{Hop Latency} (measured in nanoseconds), \textbf{Instantaneous Queue Depth}, and \textbf{Congestion Mark}.
        \item Egress sink switches strip the INT telemetry headers and forward raw telemetry digests directly to the DRL inference engine via high-speed UDP streams or Kafka event buses.
    \end{itemize}

    \item \textbf{Design Justification for the Current Prototype:}
    Although P4/INT represents the definitive future for hardware merchant silicon, this project deliberately deploys OpenFlow 1.3 on Open vSwitch (OVS) and Mininet for the primary software prototype. OpenFlow 1.3 is universally supported across commodity Linux network namespaces without requiring specialized P4 compiler toolchains (p4c) or proprietary FPGA/ASIC hardware emulators. Crucially, the 10-dimensional state vector $\mathbf{s} \in \mathbb{R}^{10}$ designed in this project is explicitly architected to map directly onto INT header fields, ensuring seamless future migration to P4-native hardware testbeds.
\end{enumerate}

\section{Mathematical Foundations of Traffic Engineering and UMCF}
A communication network is formally modeled as a directed multigraph $G = (V, E)$, where $V$ represents the set of network nodes (OpenFlow switches) with $|V| = N$, and $E$ represents the set of directed transmission links with $|E| = M$. Each directed edge $e = (u, v) \in E$ is characterized by:
\begin{itemize}
    \item Transmission capacity $C_e > 0$ expressed in Megabits per second (Mbps).
    \item Physical propagation delay $d_{\text{prop}}(e) > 0$ expressed in milliseconds (ms).
    \item Finite buffer queue capacity $B_e$ expressed in packets.
\end{itemize}

Let $\mathcal{K} = \{1, 2, \dots, K\}$ denote the set of active traffic demands (commodities) traversing the network. Each commodity $k \in \mathcal{K}$ is defined by a tuple:
\begin{equation}
k = \left( s_k, t_k, D_k \right)
\end{equation}
where $s_k \in V$ is the ingress source node, $t_k \in V$ is the egress destination node, and $D_k \ge 0$ is the traffic bandwidth demand (in Mbps).

Let $\mathcal{P}_k$ denote the set of loopless directed paths connecting source $s_k$ to destination $t_k$ in $G$. In modern packet networks, per-packet multi-path routing across paths with asymmetric latencies causes severe TCP packet reordering, duplicate ACKs, and catastrophic throughput collapse. Consequently, this work operates strictly within the \textbf{Unsplittable Multi-Commodity Flow (UMCF)} regime. For each demand $k$, we define a binary routing decision variable:
\begin{equation}
x_{k, p} \in \{0, 1\} \quad \forall p \in \mathcal{P}_k
\end{equation}
such that exactly one candidate path is assigned to each demand:
\begin{equation}
\label{eq:path_assignment}
\sum_{p \in \mathcal{P}_k} x_{k, p} = 1 \quad \forall k \in \mathcal{K}
\end{equation}

The aggregate traffic load $\lambda_e$ traversing link $e \in E$ is the sum of bandwidth demands of all commodities routed through link $e$:
\begin{equation}
\lambda_e = \sum_{k \in \mathcal{K}} \sum_{p \in \mathcal{P}_k : e \in p} D_k \cdot x_{k, p} \quad [\text{Mbps}]
\end{equation}
The instantaneous utilization $u_e$ of link $e$ is defined as the ratio of traffic load to physical capacity:
\begin{equation}
u_e = \frac{\lambda_e}{C_e}
\end{equation}

To prevent packet loss, physical link capacity constraints enforce:
\begin{equation}
\label{eq:capacity_constraint}
u_e \le 1.0 \quad \forall e \in E \iff \lambda_e \le C_e
\end{equation}

The general Traffic Engineering objective is to find a binary path assignment matrix $\mathbf{X} = \{x_{k, p}\}$ that minimizes a composite network cost function $\Psi(\mathbf{X})$ while satisfying (\ref{eq:path_assignment}) and (\ref{eq:capacity_constraint}):
\begin{equation}
\min_{\mathbf{X}} \quad \Psi(\mathbf{X}) = \sum_{e \in E} \Phi(u_e) + \alpha \sum_{k \in \mathcal{K}} \text{Delay}(k, \mathbf{X}) + \beta \sum_{k \in \mathcal{K}} \text{Jitter}(k, \mathbf{X})
\end{equation}
where $\Phi(u_e)$ is a convex link congestion penalty function.

\begin{theorem}[NP-Hardness of UMCF]
The Unsplittable Multi-Commodity Flow problem with binary decision variables $x_{k, p} \in \{0, 1\}$ is NP-hard (weakly NP-hard in basic two-node graphs and strongly NP-hard in general directed topologies) \cite{garey1979computers, even1976complexity}.
\end{theorem}
\begin{proof}
The proof proceeds by reduction from the classical \textsc{Partition} problem. Given a finite set of positive integers $\mathcal{S} = \{w_1, w_2, \dots, w_n\}$ summing to $2W$, the partition problem asks whether there exists a subset $\mathcal{S}' \subset \mathcal{S}$ such that $\sum_{i \in \mathcal{S}'} w_i = W$. We construct a 2-node graph $G=(V, E)$ with source $s$ and destination $t$ connected by two parallel directed links $e_1, e_2$, each with capacity $C_{e_1} = C_{e_2} = W$. For each integer $w_i$, define a commodity $k_i = (s, t, w_i)$. Any valid unsplittable routing assignment satisfying $u_{e_1} \le 1.0$ and $u_{e_2} \le 1.0$ corresponds directly to a valid partition of $\mathcal{S}$. Because \textsc{Partition} is NP-complete, finding an optimal unsplittable flow assignment is NP-hard. In general directed multigraphs with multiple commodities ($K \ge 2$), UMCF is strongly NP-hard via reduction from the directed two-commodity integral flow problem \cite{even1976complexity}, establishing that exact polynomial-time optimization is computationally intractable for dynamic real-time traffic engineering.
\end{proof}

\section{Queueing Delay, Bufferbloat, and RFC 3393 Jitter Modeling}
To evaluate link latency realistically without arbitrary heuristics, we model switch egress port buffers using stochastic queueing theory. Assuming Poisson packet arrivals with aggregate rate $\lambda_e$ and exponentially distributed packet transmission service times with service rate $\mu_e = C_e / \bar{L}$ (where $\bar{L}$ is the mean packet size), each switch port buffer behaves as an $M/M/1/K$ queue with finite buffer capacity $K_B$:

\begin{enumerate}
    \item \textbf{Kleinrock Mean Queueing Delay:}
    Under stable traffic regimes ($\rho_e = \lambda_e / \mu_e < 1.0$), the mean queueing delay $W_{q}(e)$ experienced by packets in the buffer is derived via Kleinrock's formula \cite{kleinrock1964communication}:
    \begin{equation}
    W_{q}(e) = \frac{\rho_e}{\mu_e(1 - \rho_e)} = \frac{\lambda_e}{\mu_e(\mu_e - \lambda_e)} \quad [\text{seconds}]
    \end{equation}
    The total end-to-end latency $D(p)$ along path $p$ is the sum of physical propagation delays and queueing delays across all constituent hops:
    \begin{equation}
    D(p) = \sum_{e \in p} \left( d_{\text{prop}}(e) + W_{q}(e) \right) \quad [\text{ms}]
    \end{equation}

    \item \textbf{Finite Buffer Packet Drop Probability:}
    When traffic approaches or exceeds capacity, the finite switch buffer overflows. The stationary probability $P_{\text{loss}}(e)$ of a packet arriving to find a full buffer (inducing tail-drop) in an $M/M/1/K_B$ queue is given by:
    \begin{equation}
    P_{\text{loss}}(e) = \frac{(1 - \rho_e)\rho_e^{K_B}}{1 - \rho_e^{K_B + 1}}
    \end{equation}
    For a path $p$, the overall packet delivery success rate is $\prod_{e \in p} (1 - P_{\text{loss}}(e))$, yielding path drop probability:
    \begin{equation}
    P_{\text{loss}}(p) = 1 - \prod_{e \in p} \left(1 - P_{\text{loss}}(e)\right)
    \end{equation}

    \item \textbf{Packet Delay Variation (Jitter, RFC 3393):}
    The Internet Engineering Task Force (IETF) RFC 3393 specifies the IP Packet Delay Variation (IPDV) metric \cite{rfc3393}. For a sequence of consecutive packets $\{1, 2, \dots, M\}$ traversing path $p$ with measured one-way transit delays $\{D_1, D_2, \dots, D_M\}$, the RFC 3393 IPDV between adjacent packets $i$ and $i+1$ is defined as the signed delay differential:
    \begin{equation}
    \text{IPDV}_i = D_{i+1} - D_i \quad [\text{ms}]
    \end{equation}
    The path-level average absolute jitter metric $J_{\text{IPDV}}(p)$ is computed as:
    \begin{equation}
    J_{\text{IPDV}}(p) = \frac{1}{M - 1} \sum_{i=1}^{M-1} \left| D_{i+1} - D_i \right| \quad [\text{ms}]
    \end{equation}
    In our telemetry simulation and routing reward formulation, the continuous queue-state proxy for delay jitter across path hops is modelled via the root-sum-square of queue delay standard deviations, $J(p) = \sqrt{\sum_{e \in p} \text{Var}(W_q(e))}$, providing a differentiable penalty that tracks delay dispersion.
\end{enumerate}

\section{Deep Reinforcement Learning Foundations}
Reinforcement learning addresses the problem of an autonomous agent learning optimal control policies through trial-and-error interactions with a dynamic environment. The underlying decision process is formulated as an infinite-horizon discounted Markov Decision Process (\textbf{MDP}), defined by the 5-tuple:
\begin{equation}
\mathcal{M} = \left( \mathcal{S}, \mathcal{A}, \mathcal{P}, \mathcal{R}, \gamma \right)
\end{equation}
where $\mathcal{S}$ is the state space, $\mathcal{A}$ is the discrete action space, $\mathcal{P}(s' | s, a) = \mathbb{P}(S_{t+1} = s' | S_t = s, A_t = a)$ represents transition probability dynamics, $\mathcal{R}(s, a)$ is the scalar reward function, and $\gamma \in [0, 1)$ is the temporal discount factor.

The agent's goal is to learn a policy $\pi(a | s)$ that maximizes the expected cumulative discounted return $G_t$:
\begin{equation}
G_t = \sum_{k=0}^{\infty} \gamma^k R_{t+k+1}
\end{equation}
Under policy $\pi$, the state-action value function $Q^\pi(s, a)$ satisfies the fundamental Bellman equation \cite{sutton2018reinforcement}:
\begin{equation}
Q^\pi(s, a) = \mathbb{E}\left[ R_{t+1} + \gamma \sum_{a' \in \mathcal{A}} \pi(a' | S_{t+1}) Q^\pi(S_{t+1}, a') \;\middle|\; S_t = s, A_t = a \right]
\end{equation}
The optimal action-value function $Q^*(s, a) = \max_\pi Q^\pi(s, a)$ satisfies the non-linear Bellman optimality equation:
\begin{equation}
Q^*(s, a) = \mathbb{E}\left[ R_{t+1} + \gamma \max_{a' \in \mathcal{A}} Q^*(S_{t+1}, a') \;\middle|\; S_t = s, A_t = a \right]
\end{equation}

\section{Dueling Double Deep Q-Networks (D3QN)}
In high-dimensional state spaces, tabular Q-learning fails due to the curse of dimensionality. Deep Q-Networks (DQN) \cite{mnih2015human} approximate $Q^*(s, a)$ using a deep neural network parameterized by weights $\theta$. However, standard DQN suffers from two critical flaws in network routing:
\begin{enumerate}
    \item \textbf{Severe Q-Value Overestimation Bias:} The maximization operator $\max_{a'} Q(s', a'; \theta)$ systematically overestimates action values in noisy networking environments.
    \item \textbf{Representational Inefficiency:} In many routing states, the underlying state value $V(s)$ (overall network health) is critical, regardless of which candidate path is chosen.
\end{enumerate}

To overcome these deficiencies, this work implements a \textbf{Dueling Double Deep Q-Network (D3QN)} combining two architectural breakthroughs:

\begin{enumerate}
    \item \textbf{Double Q-Learning Target Decoupling:}
    Van Hasselt et al. \cite{vanhasselt2016deep} showed that decoupling action selection from action evaluation can reduce maximization bias. Action selection is governed by the online network parameters $\theta$, while target evaluation is governed by a delayed target network $\theta^-$:
    \begin{equation}
    \label{eq:double_q_target}
    Y_t^{\text{DDQN}} = R_{t+1} + \gamma Q\left(S_{t+1}, \arg\max_{a' \in \mathcal{A}} Q(S_{t+1}, a'; \theta); \theta^-\right)
    \end{equation}
    The target network parameters $\theta^-$ are smoothly tracked via Polyak soft updates with coefficient $\tau = 0.005$:
    \begin{equation}
    \theta^- \leftarrow \tau \theta + (1 - \tau)\theta^-
    \end{equation}

    \item \textbf{Dueling Neural Network Stream Factorization:}
    Wang et al. \cite{wang2016dueling} introduced the Dueling architecture, which factorizes the representation into two separate streams following shared feature extraction:
    \begin{itemize}
        \item A scalar State-Value stream $V(s; \theta, \beta) \in \mathbb{R}$.
        \item A vector Action-Advantage stream $A(s, a; \theta, \alpha) \in \mathbb{R}^{|\mathcal{A}|}$.
    \end{itemize}
    To guarantee identifiability (preventing arbitrary scalar offsets between $V$ and $A$), the aggregation layer enforces mean-centering:
    \begin{equation}
    \label{eq:dueling_aggregation}
    Q(s, a; \theta, \alpha, \beta) = V(s; \theta, \beta) + \left( A(s, a; \theta, \alpha) - \frac{1}{|\mathcal{A}|} \sum_{a' \in \mathcal{A}} A(s, a'; \theta, \alpha) \right)
    \end{equation}
\end{enumerate}

\section{Prioritized Experience Replay (PER) with Binary SumTree}
Standard DQN samples past transitions uniformly from a memory buffer. However, in network routing, catastrophic congestion events (such as buffer drops and link failures) are rare but critical. Uniform sampling drowns these rare events in seas of normal traffic. 

Prioritized Experience Replay (PER) \cite{schaul2016prioritized} samples transitions with probability proportional to their Temporal Difference (TD) error magnitude $\delta_i$:
\begin{equation}
\delta_i = Y_i^{\text{DDQN}} - Q(s_i, a_i; \theta)
\end{equation}
The priority $p_i$ of transition $i$ is formalized as:
\begin{equation}
p_i = \left( |\delta_i| + \epsilon_{\text{per}} \right)^\alpha
\end{equation}
where $\epsilon_{\text{per}} = 10^{-5}$ guarantees non-zero priority, and $\alpha \in [0, 1]$ controls prioritization aggressiveness ($\alpha = 0$ corresponds to uniform sampling, while $\alpha = 0.6$ is the canonical default empirically recommended by Schaul et al.~\cite{schaul2016prioritized} to balance priority sampling against diversity). The sampling probability $P(i)$ is:
\begin{equation}
P(i) = \frac{p_i}{\sum_{k=1}^N p_k}
\end{equation}

Non-uniform sampling introduces distribution bias. To ensure unbiased stochastic gradient descent, importance-sampling (IS) weights $w_i$ are computed:
\begin{equation}
w_i = \left( \frac{1}{N \cdot P(i)} \right)^\beta \Big/ \max_{j} w_j
\end{equation}
where $\beta$ is annealed linearly from $\beta_0 = 0.4$ to $1.0$ during training.

To avoid costly $O(N)$ linear scans when sampling and updating priorities over buffers with $N = 50,000$ transitions, we implement a \textbf{Binary SumTree}. A SumTree is a complete binary tree where:
\begin{itemize}
    \item The root node stores the total cumulative priority sum $p_{\text{total}} = \sum_{k=1}^N p_k$.
    \item Each parent node equals the exact sum of its two children: $P_{\text{parent}} = P_{\text{left}} + P_{\text{right}}$.
    \item Leaf nodes store the individual transition priorities $p_i$.
\end{itemize}
Both sample retrieval and priority updates execute in strictly $O(\log N)$ time, enabling real-time training steps without control plane stalling.

\section{Overview and Taxonomy of Traffic Engineering}
Traffic Engineering (TE) has evolved across three major technological paradigms:
\begin{enumerate}
    \item \textbf{Distributed Classical Heuristics (1990--2005):} Protocols such as OSPF, IS-IS, and early MPLS-TE operated distributed routing computations with static administrative weights.
    \item \textbf{Centralized SDN Optimization (2008--2016):} Decoupled control planes enabled centralized linear solvers (e.g., Hedera \cite{al2010hedera}, Google B4 \cite{jain2013b4}, Microsoft SWAN \cite{hong2013achieving}).
    \item \textbf{Learning-Driven and AI-Based TE (2017--Present):} Machine learning, deep reinforcement learning, and graph neural networks deployed for autonomous routing adaptation.
\end{enumerate}

\section{Classical Heuristic and Static Metric Optimization}
The earliest formalization of IP traffic engineering focused on optimizing static OSPF/IS-IS link metrics. Fortz and Thorup \cite{fortz2000internet, fortz2002optimizing} proved that optimizing link weights to minimize a piecewise-linear convex congestion function is NP-hard. They proposed local search heuristics to tune static weights. However, static weight tuning assumes quasi-static traffic matrices; under dynamic microbursts, static weights cannot adapt, inducing severe localized bottlenecks.

Equal-Cost Multi-Path (ECMP) \cite{moy1998ospf} hashes packet 5-tuples (source IP, destination IP, protocol, source port, destination port) across paths with identical administrative cost. However, ECMP cannot route traffic over paths with even one additional hop, leaving viable edge-disjoint paths unused. Furthermore, hash collisions between long-lived ``elephant flows'' cause persistent link saturation and packet drops.

\section{Centralized SDN Heuristics and Linear Solvers}
The emergence of OpenFlow \cite{lanzisera2010openflow} enabled centralized global visibility. Al-Fares et al. introduced \textbf{Hedera} \cite{al2010hedera}, a dynamic flow management system for multi-rooted Fat-Tree datacenter topologies. Hedera monitors flow rates on edge switches and dynamically computes multi-commodity flow allocations for flows exceeding $10\%$ of link capacity using a greedy heuristic. However, Hedera relies on heuristic path hunting that does not learn from historical traffic dynamics.

Google deployed \textbf{B4} \cite{jain2013b4}, a private software-defined WAN connecting global datacenters. B4 employs centralized Traffic Engineering servers that solve linear programs periodically (every few minutes) to allocate bandwidth based on application priority classes. Similarly, Microsoft developed \textbf{SWAN} \cite{hong2013achieving}, which coordinates inter-datacenter transfers using centralized constrained optimization. While effective for predictable bulk transfers, the solver latency of linear programs (spanning tens of seconds to several minutes) renders them incapable of reacting to sub-second microbursts or transient localized buffer bloat.

\section{Deep Reinforcement Learning in Network Routing}
In recent years, deep reinforcement learning has been explored for network routing:
\begin{itemize}
    \item \textbf{Stampa et al. (2017):} \cite{stampa2017deep} introduced a standard Deep Q-Network (DQN) for SDN routing optimization, demonstrating delay reduction on a 14-node network. However, their system utilized a standard flat DQN (suffering from overestimation bias), uniform experience replay, and an unpenalized reward function that neglected packet loss and jitter.
    \item \textbf{Valadarsky et al. (2017):} \cite{valadarsky2017learning} proposed DRL-TE, applying policy gradient methods to optimize split ratios. However, their action space scaled combinatorially with network size, preventing convergence on larger topologies.
    \item \textbf{Aurochs (Chen et al., 2018):} \cite{chen2018aurochs} designed a data-driven TE framework for enterprise networks, but relied on slow offline training pipelines without closed-loop real-time failover.
    \item \textbf{RL-Routing (Chen et al., 2020):} \cite{chen2020rlrouting} proposed an SDN routing algorithm based on standard Deep Q-Networks evaluated against OSPF and Least-Loaded Routing on topologies such as NSFNet. While RL-Routing demonstrated the potential of model-free reinforcement learning in OpenFlow environments, it relied on a single-stream Q-network (susceptible to maximization bias), uniform random experience replay (which fails to prioritize critical tail-congestion events), unconstrained next-hop decisions (which can create transient routing loops or dead ends without topological action masking), and an idealized single-controller architecture without high-availability failover.
    \item \textbf{RouteNet and RouteNet-Fermi (Rusek et al., 2020; Almasan et al., 2022):} \cite{rusek2019routenet, almasan2022routenet} leveraged Graph Neural Networks (GNNs) to model the non-linear relationship between topology, traffic matrix, and packet-level delay/jitter distributions. While RouteNet-Fermi achieves structural scale-invariance across arbitrary topologies, it operates primarily as an offline digital-twin forward performance evaluator rather than an autonomous closed-loop routing actuator, relying on external meta-heuristic search to select forwarding paths.
    \item \textbf{Multi-Path DRL Routing (Sun et al., 2021):} \cite{sun2021multi} developed multi-path DRL traffic engineering with dynamic split-ratio tuning over OpenFlow. However, per-packet multi-path splitting introduces significant TCP out-of-order delivery penalties, underscoring the necessity of unsplittable flow allocation for real-time transport streams.
    \item \textbf{Multi-Agent SDN TE (Xu et al., 2022):} \cite{xu2022multiagent} explored multi-agent reinforcement learning for large-scale multi-domain SDN, decomposing wide-area routing into regional sub-controllers. While reducing state dimension per agent, inter-controller communication overhead and non-stationarity during joint exploration remain significant deployment challenges.
\end{itemize}

\section{High Availability and Resilience in SDN Control Planes}
Carrier networks may target $99.999\%$ availability (maximum 5.26 minutes of downtime per year). Distributed controllers such as ONOS and OpenDaylight provide clustering mechanisms. Many DRL-for-routing evaluations nevertheless treat the controller as an idealized single-node abstraction, making controller-crash recovery, socket reconnection, and state synchronization comparatively less explored in the selected routing literature.

\section{Research Gap and Key Innovations}
The critical review of existing literature reveals four major research gaps:
\begin{enumerate}
    \item \textbf{Gap 1: Q-Value Overestimation and Action Explosion:} Existing DRL routing approaches use flat DQN architectures that suffer from catastrophic overestimation bias, or unconstrained action spaces that scale exponentially ($O(|V|^2)$), preventing real-time convergence.
    \item \textbf{Gap 2: Loss of Critical Congestion Transitions in Replay:} Standard uniform replay buffers discard or severely dilute rare buffer overflow and link saturation events, causing agents to unlearn defensive rerouting policies.
    \item \textbf{Gap 3: Complete Neglect of Controller High Availability:} Prior DRL-TE publications assume an infallible centralized controller, omitting failover latency, leader election, and state synchronization.
    \item \textbf{Gap 4: Lack of Statistical and Zero-Shot Transfer Rigor:} Most studies evaluate on a single topology under static Poisson traffic, omitting multi-seed ANOVA decomposition and zero-shot transfer evaluations on unvisited graph topologies.
\end{enumerate}

The platform developed in this project directly addresses and resolves all four research gaps.

The closed loop operates continuously:
\begin{enumerate}
    \item Open vSwitch (OVS) switches in the Data Plane execute packet forwarding via TCAM flow tables.
    \item The Ryu controller polls port counters every $\Delta t = 1.0$~s using \code{OFPPortStatsRequest}.
    \item First-order differentials $\Delta tx\_bytes$ are computed to derive instantaneous link load $\lambda_e(t)$ and utilization $u_e(t) = \lambda_e(t) / C_e$.
    \item The State Encoder synthesizes a normalized 10-dimensional telemetry vector $\mathbf{s}_t \in \mathbb{R}^{10}$.
    \item The PyTorch D3QN engine performs a forward inference pass ($0.24$~ms) to select the optimal loopless path $a_t^* = \arg\max_a Q(\mathbf{s}_t, a)$.
    \item The FlowMod Dispatcher generates \code{OFPFlowMod} messages instructing switches to program corresponding forwarding rules.
    \item Experiences $(\mathbf{s}_t, a_t, r_t, \mathbf{s}_{t+1}, d_t)$ are stored in the binary SumTree PER buffer for asynchronous training.
\end{enumerate}

\paragraph{Handling Variable Candidate Path Counts and Invalid Action Masking:}
When the network topology does not yield $K=4$ loopless paths between an ingress-egress pair (e.g., in sparse meshes where only two loopless paths exist), two complementary mechanisms ensure mathematical consistency:
\begin{enumerate}
    \item \textbf{Penalty Feature Padding:} For any candidate index $i \ge \text{candidate\_count}$, the state manager sets $\hat{u}_i = 1.0$ and $\hat{D}_i = 1.0$. This ensures the input tensor maintains a fixed dimension $\mathbb{R}^{10}$ while providing an immediate penalty signal to the neural network.
    \item \textbf{Dynamic Invalid-Action Masking:} In the policy network forward pass (\code{agent/dqn_router.py}), action selection is restricted to physically available candidate paths via dynamic tensor slicing:
    \begin{equation}
    a^* = \arg\max_{a \in \{0, \dots, K_{\text{avail}}-1\}} Q(\mathbf{s}, a)
    \end{equation}
    where $K_{\text{avail}} = \min(K, \text{candidate\_count})$. In exploration mode ($\epsilon$-greedy), uniform random selection is similarly constrained to $\{0, \dots, K_{\text{avail}}-1\}$. This guarantees that the agent never selects a non-existent candidate route.
\end{enumerate}

\paragraph{Fixed Summary Path Features vs. True Graph Invariance:}
This 10-dimensional state representation operates on \emph{summary path statistics} rather than raw graph adjacency matrices. This design choice enables the model to ingest paths from different topologies without changing neural network weights or tensor dimensions. However, this is distinct from true graph permutation equivariance (such as that offered by Message-Passing Graph Neural Networks); our zero-shot generalization findings represent empirical transfer over the tested graph distributions, rather than a theoretical proof of arbitrary graph invariance.

Yen's algorithm computes loopless paths sequentially:
\begin{enumerate}
    \item The 1st shortest path $P_1$ is obtained via standard Dijkstra search.
    \item To find path $P_k$, each node along $P_{k-1}$ serves as a deviation node $v_{\text{dev}}$. Edges participating in previous paths sharing the same root are temporarily masked from $G$.
    \item A spur path is computed from $v_{\text{dev}}$ to the destination. Concatenating root and spur produces a loopless candidate.
    \item The candidate is placed in a priority queue $B$. The shortest candidate in $B$ becomes $P_k$.
\end{enumerate}
This formulation bounds the action space to $|\mathcal{A}| = K = 4$, guaranteeing loop-freedom and ensuring $O(1)$ decision complexity.

    \item \textbf{Input Layer:} 10 continuous neurons accepting the state vector $\mathbf{s} \in \mathbb{R}^{10}$.

    \item \textbf{Value Stream $V(s)$ ($8,449$ parameters):} Dense layer ($128 \to 64$ units, $8,256$ weights) with \code{LayerNorm} ($128$ weights), ReLU activation, and final linear scalar projection ($64 \to 1$, $65$ weights) outputting $V(s) \in \mathbb{R}$.
    \item \textbf{Advantage Stream $A(s, a)$ ($8,644$ parameters):} Dense layer ($128 \to 64$ units, $8,256$ weights) with \code{LayerNorm} ($128$ weights), ReLU activation, and final linear vector projection ($64 \to 4$, $260$ weights) outputting $A(s, a) \in \mathbb{R}^4$.
    \item \textbf{Aggregation Layer ($0$ trainable parameters):} Mean-centered advantage aggregation yielding $Q(s, a)$ via (\ref{eq:dueling_aggregation}).
    \item \textbf{Total Model Parameters:} $9,408 + 8,449 + 8,644 = \mathbf{26,501}$ trainable parameters, perfectly matching the inspected PyTorch runtime weights and Appendix~\ref{app:manual}.
\end{itemize}

\subsection{Implemented Multi-Objective Reward Function}
The controller implementation uses a weighted heuristic reward. It penalizes hops, delay, jitter, loss, and bottleneck utilization, with an additional quadratic term after a configurable threshold. This is the function used by \code{controller/routing_module.py}; it should not be interpreted as a formal safety barrier.
\begin{equation}
\label{eq:reward_full}
R(p) = -\left(w_H H(p) + w_D D(p) + w_J J(p) + w_L L(p) + \Gamma(u_{\max})\right)
\end{equation}
The checked-in defaults are $w_H=0.35$, $w_D=0.06$, $w_J=0.25$, and $w_L=0.50$. With $\theta=0.70$ and $w_C=1.0$, the congestion term is:
\begin{equation}
\label{eq:barrier_function}
\Gamma(u) = w_Cu^2 + 12w_C\max(0,u-\theta)^2.
\end{equation}
Unlike a rational or logarithmic barrier, $\Gamma$ is finite and remains well-defined when the simulator represents overload with $u>1$. The state encoder clips normalized input features to $[0,1]$, while the queue model retains overload values when estimating delay and loss. Consequently, this term encourages avoidance of loaded paths but cannot guarantee zero loss or enforce a hard capacity constraint.

\paragraph{Architecture and Failover Mechanics:}
The multi-controller pool operates as follows:
\begin{itemize}
    \item \textbf{Normal Operation:} Controller 1 serves as the active primary (OpenFlow port 6633, REST port 8080). Controllers 2 and 3 operate as warm standby nodes on separate ports (6634/8081 and 6635/8082). Open vSwitch instances are configured with multi-controller target strings (\code{tcp:127.0.0.1:6633}, \code{tcp:127.0.0.1:6634}, \code{tcp:127.0.0.1:6635}).
    \item \textbf{Health Probing and Failure Detection:} Node vitality is probed via HTTP GET \code{/api/health} with a configurable timeout ($\le 1.0$~s).
    \item \textbf{Local Promotion Bookkeeping ($0.001$~ms):} When failover is triggered, the pool updates its internal active index pointer and appends an event to the failover history log. In Python, this memory pointer reassignment and dictionary bookkeeping executes in \textbf{0.001~ms} (1.0~$\mu$s).
    \item \textbf{End-to-End Client HTTP Recovery ($37.96$~ms):} Client REST requests dispatched via \code{execute_request()} catch socket connection errors (\code{ConnectionRefusedError}, \code{URLError}) and automatically retry against the next healthy standby node, completing full end-to-end client HTTP recovery in \textbf{37.96~ms}.
    \item \textbf{Data-Plane Continuity Limitation:} Existing Open vSwitch flow entries can continue forwarding while the controller process is unavailable. This behavior was not measured as an end-to-end, loss-free failover guarantee; flows requiring new rules or state recovery may be affected.
\end{itemize}

Traffic workloads are generated using a multi-profile synthetic traffic engine (\code{topology/traffic_generator.sh}):
\begin{itemize}
    \item \textbf{Poisson Background Workload:} Packet inter-arrival times follow an exponential distribution with rate $\lambda_{\text{bg}}$, emulating web traffic and DNS queries.
    \item \textbf{Bursty Pareto Elephant Flows:} Heavy-tailed bursty transfers with shape parameter $\alpha = 1.2$, generating massive burst transfers that induce sudden buffer bloat.
    \item \textbf{Asymmetric Core Link Jamming:} Adversarial workload concentrating $95\%$--$96\%$ of traffic across a single core transit path (invoked via \code{inject_core_congestion(utilization=0.96)}) to rigorously test proactive bypass rerouting.
\end{itemize}

\subsection{Baseline Routing Protocols for Comparative Tournament}
The D3QN platform is evaluated head-to-head against four standard routing protocols:
\begin{enumerate}
    \item \textbf{OSPF (RFC 2328) \cite{moy1998ospf}:} Standard shortest path routing using inverse capacity link weights.
    \item \textbf{Dijkstra Shortest Path First (SPF) \cite{dijkstra1959note}:} Hop-count shortest path routing.
    \item \textbf{Equal-Cost Multi-Path (ECMP):} Hash-based flow splitting across strictly equal-cost paths.
    \item \textbf{Widest Shortest Path (WSP):} Selects the path with maximum residual bottleneck capacity among minimum-hop paths.
    \item \textbf{Greedy Least-Loaded Routing (LLR):} Dynamically selects the candidate path with lowest instantaneous bottleneck utilization.
\end{enumerate}

\section{Testing and Evaluation}
\label{sec:testing}

\subsection{Key Performance Metrics}
Performance is evaluated across six rigorous quantitative metrics:
\begin{enumerate}
    \item \textbf{Peak Bottleneck Link Utilization ($u_{\max}$):} Maximum utilization across all links, $\max_{e} u_e$ (\lowerbetter).
    \item \textbf{End-to-End Latency ($D$):} Mean packet transit delay in milliseconds (\lowerbetter).
    \item \textbf{Packet Delay Variation (Jitter, RFC 3393) ($J$):} Standard deviation of packet delays in milliseconds (\lowerbetter).
    \item \textbf{Packet Drop Rate ($P_{\text{loss}}$):} Percentage of transmitted packets dropped due to buffer overflow (\lowerbetter).
    \item \textbf{Jain's Fairness Index ($\mathcal{J}$):} Quantifies bandwidth allocation fairness across commodities \cite{jain1984quantitative}:
    \begin{equation}
    \mathcal{J} = \frac{\left( \sum_{k=1}^K x_k \right)^2}{K \sum_{k=1}^K x_k^2} \quad (\higherbetter)
    \end{equation}
    \item \textbf{High-Availability Failover Latency ($\tau_{\text{fail}}$):} Milliseconds required to promote a standby controller and resume client HTTP REST service (\lowerbetter).
\end{enumerate}

Quantitative metrics from the recorded ablation evaluations (\code{ablation_study_results.json}) demonstrate:
\begin{itemize}
    \item \textbf{Impact of Double Q-Learning:} Standard single-stream DQN (Chen et al. \cite{chen2020rlrouting}) exhibits significant Q-value overestimation bias under dynamic bursty traffic, resulting in a mean latency of $1114.89$~ms and $26.24\%$ loss. Introducing Double Q-learning decouples action selection from target evaluation, mitigating overestimation bias and reducing mean latency to $1060.27$~ms and loss to $23.37\%$.
    \item \textbf{Impact of Dueling Network Factorization:} Decoupling state value $V(s)$ from candidate path advantages $A(s, a)$ enables the network to identify states of general network congestion regardless of path choice. This yields the single largest performance jump: mean latency drops by over $50\%$ to $529.99$~ms, and packet loss is reduced to $15.11\%$.
    \item \textbf{Impact of Binary SumTree Prioritized Experience Replay (PER):} Uniform replay buffers dilute rare buffer-overflow and link-saturation transitions in seas of nominal traffic. The binary SumTree PER engine ensures that transitions with high TD error magnitude $\delta_i$ are sampled proportionally with $O(\log N)$ algorithmic complexity, accelerating training stability and preventing the agent from unlearning defensive rerouting under severe congestion bursts.
\end{itemize}

\subsection{Comparison Against Theoretical Optimal HiGHS MILP Solver}
To establish an exact theoretical reference bound, the Unsplittable Multi-Commodity Flow (UMCF) problem was formulated as a mixed-integer linear program (MILP) and solved to global optimality using the HiGHS branch-and-cut solver via \code{scipy.optimize.milp} (\code{experiment_phase1_suite.py}).

\paragraph{MILP Optimization Formulation:}
Given active commodities $\mathcal{K}$ with bandwidth demands $d_k$, candidate path sets $\mathcal{P}_k$, and directional edge capacities $C_e$:
\begin{align}
\min_{\alpha, \mathbf{x}} \quad & \alpha \\
\text{subject to} \quad & \sum_{p \in \mathcal{P}_k} x_{k, p} = 1 \quad \forall k \in \mathcal{K} \label{eq:milp_choice} \\
& \sum_{k \in \mathcal{K}} \sum_{p \in \mathcal{P}_k : e \in p} d_k x_{k, p} \le \alpha \cdot C_e \quad \forall e \in E \label{eq:milp_cap} \\
& x_{k, p} \in \{0, 1\} \quad \forall k \in \mathcal{K}, \, p \in \mathcal{P}_k, \quad 0 \le \alpha \le 5.0
\end{align}
Constraint~(\ref{eq:milp_choice}) enforces unsplittable single-path assignment. Constraint~(\ref{eq:milp_cap}) minimizes the global maximum link utilization multiplier $\alpha$. Solver feasibility and optimality tolerances were configured to $10^{-6}$. In all benchmark evaluations, HiGHS terminated with \code{status = 0}, verifying that $\alpha^*$ represents the proven global optimum under the candidate path sets.

Figure~\ref{fig:oracle_gap} illustrates the optimality gap comparisons across benchmark fabrics.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.80\textwidth]{optimisation_oracle_gap.png}
\caption{Optimality Gap Between D3QN and the Exact HiGHS MILP Solver.}
\label{fig:oracle_gap}
\end{figure}

\paragraph{Quantitative Gaps and Computational Complexity:}
From the empirical results stored in \code{optimisation_oracle_results.json}:
\begin{itemize}
    \item \textbf{Hierarchical Tree (7 Switches, 20 Flows):} The proven theoretical optimal peak load is $\alpha^* = 47.39\%$. Static Dijkstra SPF produces a peak utilization of $98.46\%$ (an optimality gap of $107.76\%$), while ECMP induces severe congestion at $112.87\%$ (gap of $138.16\%$). In contrast, D3QN achieves a peak load of \textbf{78.74\%} (gap of \textbf{66.15\%}), closing the optimality gap relative to Dijkstra SPF by \textbf{41.61 percentage points}.
    \item \textbf{NSFNet Continental Mesh (14 Switches, 20 Flows):} The theoretical optimum is $\alpha^* = 14.28\%$. D3QN achieves a peak utilization of \textbf{20.69\%} (gap of $44.89\%$), matching Dijkstra SPF while providing proactive bypass headroom.
    \item \textbf{Scope and Like-for-Like Context:} It is important to emphasize that the MILP formulation minimizes solely the peak link utilization ($\alpha$) over candidate paths on a restricted 20-flow static demand matrix, whereas D3QN optimizes a multi-objective reward (balancing delay, jitter, loss, and hop penalties alongside congestion) across a dynamic 150-flow tournament. Consequently, the MILP solver serves as an illustrative static reference ceiling rather than a direct algorithmic parity benchmark.
    \item \textbf{Execution Latency Trade-off:} In the recorded 20-flow instances, HiGHS required $61.65$--$107.59$~ms while the D3QN forward pass required $0.24$~ms in the same software environment. Neural inference scales with fixed tensor dimensions for the configured four-action model, but end-to-end control latency also includes telemetry polling, candidate generation, and OpenFlow rule installation.
\end{itemize}

The high-availability architecture operates a 3-node controller pool (Primary on port \code{6633}, Hot-Standby Backup 1 on \code{6634}, Hot-Standby Backup 2 on \code{6635}). Under empirical failure injection, performance is evaluated across two critical failure regimes:

\paragraph{Single and Cascaded Node Failures:}
When an active controller node crashes (simulating hardware fault or process termination):
\begin{itemize}
    \item \textbf{Internal Active Pointer Promotion Bookkeeping:} \textbf{0.001 ms} (1.0~$\mu$s CPU memory pointer reassignment and event logging in the local master-slave pool).
    \item \textbf{End-to-End Client HTTP REST API Recovery Time:} \textbf{37.96 ms} (transparent client HTTP retry catching socket connection refusal and redirecting to the standby endpoint).
    \item \textbf{Process Crash-to-Promotion Cascade:} \textbf{41.62--69.77 ms} (Primary $\to$ Backup 1) and \textbf{38.68--45.28 ms} (Backup 1 $\to$ Backup 2 cascaded double fault).
    \item \textbf{Failure Detection Window:} For hung or unresponsive controller processes (as opposed to immediate socket resets), watchdog heartbeat detection operates with a configurable timeout $T_{\text{detect}} \le 1.0$~second.
    \item \textbf{Data-Plane Packet Continuity:} In-flight packet loss during the control-plane transition gap was not directly instrumented on live packet traces; however, because Open vSwitch switches operate in \textbf{Fail-Secure Mode} (\code{fail_mode=secure}), switches retain committed flow table entries in kernel TCAM tables, allowing existing matching traffic to forward without interruption during control failover.
\end{itemize}

\paragraph{Total Cluster Outage Handling (What Happens When ALL Controllers Fail):}
A critical requirement of resilient network engineering is specifying behavior when all controllers in the cluster fail simultaneously (e.g., complete control-plane partition or multi-node power outage). In this platform:
\begin{enumerate}
    \item \textbf{OpenFlow Fail-Secure Autonomous Survival Mode:} OpenFlow switches transition automatically from active OpenFlow management to \textbf{Fail-Secure Mode} (\code{fail_mode=secure}). The switch kernel datapath does not purge existing flow entries upon control connection loss.
    \item \textbf{In-Flight Data-Plane Continuity:} Packets matching existing flow rules continue to be switched and forwarded at full line rate by the kernel datapath, sustaining forwarding continuity for active TCP connections and existing real-time streams.
    \item \textbf{Dynamic Route Update Suspension:} Dynamic D3QN rerouting and new flow setup computations are temporarily paused, since no active controller is available to process OpenFlow \code{OFPT_PACKET_IN} events. Unmatched new packets are queued or dropped locally at the edge rather than causing network loops.
    \item \textbf{Autonomous Self-Healing Cluster Recovery:} Background watchdog health probers continuously monitor controller socket availability. As soon as any controller node recovers (e.g., Primary reboot), the pool dynamically promotes the restored node, re-establishes OpenFlow control sessions, resumes real-time telemetry polling, and re-enables closed-loop D3QN route optimization without requiring manual network intervention.
\end{enumerate}

\subsection{Critical Discussion: Operational Trade-offs and Computational Costs}
While the empirical results demonstrate clear superiority over static heuristics, deploying DRL in production telecommunication networks entails concrete operational trade-offs:
\begin{enumerate}
    \item \textbf{Inference Latency vs. Metric Freshness:} The forward pass requires $0.216$--$0.279$~ms on commodity CPUs. While well within line-rate bounds for flow setup, the polling interval $\Delta t = 1.0$~s introduces a 1-second lag in counter updates. Reducing $\Delta t < 100$~ms increases controller control-channel overhead.
    \item \textbf{Offline Training Requirement:} The D3QN agent requires approximately 3,000 steps of offline training on simulated or emulated traffic traces to achieve convergence. Cold-starting an untrained agent directly on live production links is prohibited due to exploratory packet drops.
    \item \textbf{Switch Flow Table TCAM Capacity:} Dynamic per-flow rule installation consumes OpenFlow switch TCAM entries. On enterprise hardware with limited TCAM (e.g., 2,000 flow rules), wild-card flow aggregation or elephant-flow filtering must be employed.
\end{enumerate}

\subsection{Threats to Validity and Mitigation Strategies}
\begin{itemize}
    \item \textbf{Internal Validity:} Verified through deterministic random seeding, automated 42-test continuous integration, and identical background traffic conditions across baseline comparisons.
    \item \textbf{Construct Validity:} Key performance indicators follow standard IETF IPPM specifications: RFC 2679 for one-way delay, RFC 2680 for packet loss, and RFC 3393 for packet delay variation (jitter). Baseline routing protocol mechanics are benchmarked against RFC 2328 (OSPF v2).
    \item \textbf{External Validity:} Evaluated across five diverse topologies and generalized to random small-world graphs. Hardware ASIC testing on Barefoot Tofino is identified as the next evolutionary step.
\end{itemize}

\chapter{Conclusion}
\label{chap:conclusion}

\section{Restatement of the Problem}
Modern telecommunication backbones and cloud datacenter fabrics are constrained by static shortest path routing protocols (OSPF, ECMP) that remain decoupled from instantaneous buffer occupancy. Under asymmetric microbursts, these protocols persistently overload identical shortest paths, inducing severe core link saturation, bufferbloat, tail-drop packet loss, and RFC 3393 jitter, while viable edge-disjoint bypass paths remain idle.

\section{Summary of Proposed System and Methodology}
To address these limitations, this graduation project designed, formalized, and implemented an autonomous closed-loop Adaptive Traffic Engineering prototype powered by Deep Reinforcement Learning (DRL) over an OpenFlow 1.3 SDN substrate. Its routing results are reproducible software-model evaluations; the repository also supplies a separate packet-level Mininet/OVS protocol for confirmatory emulation. The system integrates:
\begin{itemize}
    \item A Dueling Double Deep Q-Network (D3QN) that factorizes state value $V(s)$ from action advantage $A(s, a)$ and uses Double-DQN targets to reduce overestimation bias.
    \item A binary SumTree Prioritized Experience Replay (PER) engine that achieves $O(\log N)$ proportional sampling, retaining rare congestion transitions.
    \item A multi-objective reward formulation incorporating modelled queueing delay, jitter, drop penalties, and a thresholded quadratic congestion term that encourages bypass selection under load.
    \item Candidate route pruning via Yen's $K$-shortest paths algorithm ($K=4$) with dynamic invalid-action masking, guaranteeing loop-freedom and bounded $O(1)$ decision complexity.
    \item A health-checked active/standby 3-node controller pool delivering sub-millisecond local failover bookkeeping ($0.001$~ms), cascaded process failover ($41.62$--$45.28$~ms), and transparent client HTTP recovery ($37.96$~ms).
\end{itemize}

\section{Quantitative Impact and Performance Milestones}
Benchmark tournaments across five network topologies demonstrated the following results within the stated queue and traffic model:
\begin{itemize}
    \item \textbf{53.9\% Mean Bottleneck Utilization Reduction:} Lowering arithmetic mean peak link load from $66.80\%$ to $30.80\%$ across the final seed-42 run, with the largest displayed reduction on Spine-Leaf ($99.84\% \to 20.89\%$).
    \item \textbf{71.9\% Mean Modelled Latency Reduction:} Reducing arithmetic-mean path latency from $158.34$~ms to $44.50$~ms in the final model-based tournament. This improvement is topology-dependent and most pronounced on rich multipath fabrics.
    \item \textbf{71.1\% Mean Modelled Jitter Reduction:} Reducing arithmetic-mean jitter from $9.39$~ms to $2.71$~ms in the same run ($0.515$~ms vs. $15.50$~ms on Spine-Leaf).
    \item \textbf{89.0\% Overall Modelled Packet Loss Reduction:} Reducing arithmetic-mean estimated packet drop from $4.13\%$ to $0.45\%$. Four table entries round to zero; this is not a hardware zero-loss guarantee.
    \item \textbf{High-Availability Resilience:} Achieving an internal failover pointer update latency of \textbf{0.001 ms}, cascaded process failover in \textbf{41.62--45.28 ms}, and an end-to-end client HTTP recovery time of \textbf{37.96 ms} under simulated controller process failure.
    \item \textbf{Statistical Robustness:} The checked-in multi-seed ANOVA analysis confirms that model initialization seed accounts for $<1\%$ of variance ($p = 0.80$), while topology geometry naturally dominates variance ($93.5\%$--$98.5\%$) due to physical design differences across fabrics.
\end{itemize}

\section{Restrictions, Engineering Limits, and Weaknesses}
In adherence to academic rigor, the restrictions and engineering limits of this study are candidly stated:
\begin{enumerate}
    \item \textbf{Unsplittable Forwarding Regime:} The system operates exclusively on unsplittable flow forwarding to prevent TCP packet reordering. It does not perform multi-path packet-level spraying.
    \item \textbf{Fixed Candidate Path Pool ($K=4$) and Action Masking:} While bounding action space complexity to $O(1)$, candidate paths are pre-synthesized using physical link metrics; under multi-link failure events, candidate sets must be dynamically recomputed.
    \item \textbf{Summary Path Representation vs. Structural Invariance:} The 10D state vector encodes summary path statistics rather than raw graph adjacency matrices. While enabling fixed-size transfer over tested graph distributions, it does not provide true permutation-equivariant structural invariance (such as that offered by GNNs).
    \item \textbf{Jain's Fairness Trade-Off:} In the final run, D3QN lowers mean Jain's Fairness Index ($0.697$ vs $0.768$ for OSPF), representing an operational trade-off alongside its congestion relief.
    \item \textbf{Active/Standby Controller Pool vs. Distributed Consensus:} The current resilience mechanism utilizes health probing and local standby promotion rather than a fully replicated distributed state machine (such as Raft with quorum voting and log replication).
    \item \textbf{Software Emulation Boundary:} The empirical validation was conducted inside Linux network namespaces using Open vSwitch. Hardware ASIC testing on Barefoot Tofino or Broadcom StrataXGS hardware was not performed due to physical laboratory constraints.
    \item \textbf{Empirical Packet-Level Mininet Emulation Scope:} The 120-trial empirical Mininet evaluation demonstrates that D3QN sustains high line-rate throughput (up to $48.69\text{ Mbps}$) with sub-millisecond inference ($0.52$--$0.76\text{ ms}$). However, the empirical packet measurements also reveal clear operational boundaries: under TCP workloads on rich multipath fabrics, D3QN incurs higher packet loss ($36.0\%$) than static SPF ($18.0\%$) due to window interactions with dynamic route adaptation, and on single-bottleneck tree topologies, the lightweight LLR heuristic delivers higher throughput ($38.09\text{ Mbps}$) with zero loss compared to D3QN ($34.08\text{ Mbps}$ and $10.0\%$ loss). These empirical findings confirm that DRL traffic engineering is not a universal panacea, but rather an advanced optimization framework best suited for rich multipath fabrics with diverse candidate routing paths.
\end{enumerate}

\chapter{Future Work}
\label{chap:future}

Building upon the successful empirical validation of this graduation project, six concrete research directions are identified to advance the platform toward multi-domain commercial carrier deployment:

\section{P4 Programmable Data Planes and In-Band Network Telemetry}
The current software architecture polls switch port counters every $\Delta t = 1.0$~s via OpenFlow \code{OFPPortStatsRequest}. Future work will transition the data plane from OpenFlow to \textbf{P4 (Programming Protocol-Independent Packet Processors)} running on Intel Barefoot Tofino ASICs. Implementing \textbf{In-Band Network Telemetry (INT)} will enable switches to insert hardware timestamps and queue occupancy directly into packet headers, providing sub-microsecond telemetry without control plane polling overhead.

\section{Multi-Agent RL for Inter-Domain Carrier Transit}
Modern global networks span multiple Autonomous Systems (ASes) managed by independent carriers. Future research will extend the single D3QN agent into a \textbf{Multi-Agent Reinforcement Learning (MARL)} framework, using centralized training with decentralized execution (CTDE) to coordinate inter-domain traffic engineering across peer networks while preserving administrative data privacy.

\section{Graph Neural Networks for Topological Invariance}
While the 10D normalized state representation demonstrated strong zero-shot generalization on small-world graphs, future iterations will integrate \textbf{Graph Neural Networks (GNNs)} (such as Graph Attention Networks, GAT) directly into the DRL encoder. This will enable the policy network to ingest arbitrary topological graphs as native edge-node embeddings, achieving complete topological scale invariance.

\section{Constrained MDPs and Formal Safety Verification}
To completely eliminate exploratory packet drops during online continuous learning, future research will formulate routing as a \textbf{Constrained Markov Decision Process (C-MDP)}. Leveraging Control Barrier Functions (CBFs) and Lyapunov-based safety layers will provide mathematical guarantees that exploratory routing actions never violate physical link capacity constraints.

\section{Optical Transport Network and Reconfigurable Wavelength Routing}
Extending the platform beyond layer-3 packet switching into optical transport networks (OTN) will enable the DRL agent to dynamically adjust Reconfigurable Optical Add-Drop Multiplexers (ROADMs), switching lightpaths and reallocating optical spectrum in response to long-term macro traffic shifts.

\section{Zero-Trust Control-Plane Cryptographic Attestation}
To defend against Byzantine adversaries and compromised switches, future work will integrate zero-trust cryptographic mutual TLS attestation and lightweight consensus verification across all inter-controller heartbeat channels.

\chapter{Mathematical Formulations and Proofs}
\label{app:math_proofs}

\section{Identifiability of the Dueling Architecture}
In the Dueling Q-network, unconstrained addition $Q(s, a) = V(s) + A(s, a)$ suffers from identifiability issues: given $Q(s, a)$, one cannot uniquely recover $V(s)$ and $A(s, a)$, as adding an arbitrary scalar constant $c$ to $V(s)$ while subtracting $c$ from all $A(s, a)$ leaves $Q(s, a)$ completely unchanged.

To guarantee identifiability, Wang et al. \cite{wang2016dueling} force the advantage function estimator to have zero mean across all actions:
\begin{equation}
Q(s, a; \theta, \alpha, \beta) = V(s; \theta, \beta) + \left( A(s, a; \theta, \alpha) - \frac{1}{|\mathcal{A}|} \sum_{a' \in \mathcal{A}} A(s, a'; \theta, \alpha) \right)
\end{equation}
\begin{proof}
Let $\tilde{A}(s, a) = A(s, a) - \frac{1}{|\mathcal{A}|} \sum_{a'} A(s, a')$. Summing over all $a \in \mathcal{A}$:
\begin{equation}
\sum_{a \in \mathcal{A}} \tilde{A}(s, a) = \sum_{a \in \mathcal{A}} A(s, a) - \sum_{a \in \mathcal{A}} \left( \frac{1}{|\mathcal{A}|} \sum_{a'} A(s, a') \right) = \sum_{a} A(s, a) - |\mathcal{A}| \cdot \frac{1}{|\mathcal{A}|} \sum_{a'} A(s, a') = 0
\end{equation}
Therefore, $\frac{1}{|\mathcal{A}|} \sum_{a \in \mathcal{A}} Q(s, a) = V(s) + 0 = V(s)$. Thus, $V(s)$ uniquely tracks the mean action-value of state $s$, guaranteeing mathematical identifiability.
\end{proof}

\chapter{Viva Voce Examination Master Guide and Technical Defenses}
\label{app:viva_voce}

This appendix provides formal mathematical proofs, architectural analyses, and algorithmic derivations addressing the core theoretical and engineering questions typically raised during viva voce graduation project examinations:

\section{Question 1: Dueling Stream Identifiability and Mean Centering}
\textbf{Examiner Query:} \emph{Why does the unconstrained addition of value and advantage streams $Q(s, a) = V(s) + A(s, a)$ fail to provide unique representation, and why is mean-centering preferred over max-centering in stochastic policy optimization?}

\paragraph{Mathematical Identifiability Problem:}
Consider the unconstrained functional decomposition:
\begin{equation}
Q(s, a; \theta, \alpha, \beta) = V(s; \theta, \beta) + A(s, a; \theta, \alpha)
\end{equation}
where $\theta$ denotes shared representation parameters, $\beta$ denotes value stream parameters, and $\alpha$ denotes advantage stream parameters. 
Given an observable scalar action-value $Q(s, a)$, there exists an uncountably infinite family of scalar shifts $c \in \mathbb{R}$ such that:
\begin{equation}
V'(s) = V(s) + c, \quad A'(s, a) = A(s, a) - c \implies V'(s) + A'(s, a) = V(s) + A(s, a) = Q(s, a)
\end{equation}
Because the mapping $(V, A) \mapsto Q$ is many-to-one, backpropagating temporal difference error gradients $\nabla Q$ through unconstrained streams causes severe representation drift: the value network $V(s)$ can diverge toward $+\infty$ while the advantage network $A(s, a)$ drifts toward $-\infty$ without altering the output $Q$-values.

\paragraph{Max-Centering versus Mean-Centering:}
Wang et al. \cite{wang2016dueling} evaluated two identifiability constraints:
\begin{enumerate}
    \item \textbf{Max-Centering Operator:}
    \begin{equation}
    Q(s, a) = V(s) + \left( A(s, a) - \max_{a' \in \mathcal{A}} A(s, a') \right)
    \end{equation}
    For the optimal action $a^* = \arg\max_{a'} Q(s, a')$, we have $A(s, a^*) = \max_{a'} A(s, a')$, which forces $Q(s, a^*) = V(s)$. This provides clear semantic meaning: $V(s)$ represents the value of the optimal action. However, the $\max$ operator introduces a non-smooth subgradient:
    \begin{equation}
    \frac{\partial Q(s, a)}{\partial A(s, a')} = 
    \begin{cases}
    1 - \mathbf{1}_{\{a' = \arg\max A\}}, & \text{if } a = a' \\
    -\mathbf{1}_{\{a' = \arg\max A\}}, & \text{if } a \neq a'
    \end{cases}
    \end{equation}
    Whenever the policy switches its greedy choice during exploration, the argmax index jumps discontinuously, causing high gradient variance and destabilizing batch updates.
    
    \item \textbf{Mean-Centering Operator (Deployed in this Work):}
    \begin{equation}
    Q(s, a) = V(s) + \left( A(s, a) - \frac{1}{|\mathcal{A}|} \sum_{a' \in \mathcal{A}} A(s, a') \right)
    \end{equation}
    The gradient of $Q(s, a)$ with respect to the advantage stream logits is:
    \begin{equation}
    \frac{\partial Q(s, a)}{\partial A(s, a')} = 
    \begin{cases}
    1 - \frac{1}{|\mathcal{A}|}, & \text{if } a = a' \\
    -\frac{1}{|\mathcal{A}|}, & \text{if } a \neq a'
    \end{cases}
    \end{equation}
    This gradient is constant, smooth, and well-behaved across the entire action space. Crucially, updating the advantage of the selected action $a$ simultaneously updates all unselected actions by $-\frac{1}{|\mathcal{A}|}$, ensuring balanced relative calibration without discontinuous policy oscillations.
\end{enumerate}

\section{Question 2: Thresholded Quadratic Congestion Penalty}
\textbf{Examiner Query:} \emph{What congestion term is actually implemented, and what does it guarantee?}

\paragraph{Answer:}
The implemented controller reward uses the finite heuristic penalty
\begin{equation}
\Gamma(u)=w_Cu^2+12w_C\max(0,u-\theta)^2, \qquad \theta=0.70,
\end{equation}
combined with hop, delay, jitter, and loss terms. The first component grows smoothly with utilization; the second increases the marginal cost above the configured threshold. It makes high-utilization candidates less attractive, but it is neither asymptotic nor a hard constraint. In particular, it cannot guarantee avoidance of loss when all candidate paths are congested. The simulator can represent $u>1$ under overload; this remains numerically well-defined for the quadratic term. Any claim of formal safety would require explicit capacity constraints or a separately verified constrained-MDP safety layer.

\section{Question 3: Binary SumTree Priority Updates and $O(\log N)$ Complexity}
\textbf{Examiner Query:} \emph{How does the Binary SumTree data structure enable scalable Prioritized Experience Replay, and what prevents numerical precision drift during continuous execution?}

\paragraph{Data Structure Architecture:}
Prioritized Experience Replay (PER) \cite{schaul2016prioritized} samples transition tuples $i$ according to priority probability:
\begin{equation}
P(i) = \frac{p_i^\alpha}{\sum_{k=1}^N p_k^\alpha}, \quad p_i = |\delta_i| + \epsilon
\end{equation}
where $\delta_i = r_i + \gamma Q(s'_i, \arg\max_a Q(s'_i, a; \theta); \theta^-) - Q(s_i, a_i; \theta)$ is the TD error, $\alpha = 0.6$, and $\epsilon = 10^{-5}$.

A naive array of size $N = 50,000$ requires $O(N)$ operations to compute prefix sums for sampling, and $O(1)$ to write, yielding unacceptable computational overhead ($50,000$ operations per mini-batch step). 
The Binary SumTree represents a complete binary tree implemented as a contiguous 1D array of size $2N - 1$:
\begin{itemize}
    \item Leaf nodes: Occupy indices $[N-1, 2N-2]$ and store individual transition priorities $p_i^\alpha$.
    \item Internal parent nodes: Occupy indices $[0, N-2]$, where each parent stores the sum of its immediate children:
    \begin{equation}
    \text{tree}[k] = \text{tree}[2k + 1] + \text{tree}[2k + 2]
    \end{equation}
    \item Root node: Index $0$ stores the exact total priority sum: $\text{tree}[0] = \sum_{k=1}^N p_k^\alpha$.
\end{itemize}

\paragraph{Sampling Mechanics in $O(\log N)$:}
To sample a mini-batch of size $B = 64$:
\begin{enumerate}
    \item Divide the total sum into $B$ equal segments: $S_b = \left[ b \cdot \frac{\text{tree}[0]}{B}, (b+1) \cdot \frac{\text{tree}[0]}{B} \right]$.
    \item Sample uniform scalar $v \sim \text{Uniform}(S_b)$.
    \item Descend from root index $k = 0$:
    \begin{itemize}
        \item If $v \le \text{tree}[2k + 1]$, branch to left child: $k \leftarrow 2k + 1$.
        \item Else, decrement target $v \leftarrow v - \text{tree}[2k + 1]$ and branch to right child: $k \leftarrow 2k + 2$.
    \end{itemize}
    \item Terminate when a leaf node is reached. The traversal depth is exactly $\lceil \log_2 N \rceil = \lceil \log_2 50,000 \rceil = 16$ operations.
\end{enumerate}

\paragraph{Priority Update Mechanics in $O(\log N)$:}
When transition $i$ is replayed, its new priority $p_{\text{new}} = (|\delta_i| + \epsilon)^\alpha$ is computed. The tree update proceeds:
\begin{equation}
\Delta = p_{\text{new}} - \text{tree}[\text{leaf\_idx}]
\end{equation}
The tree propagates this difference upward along the single ancestor path:
\begin{equation}
\text{tree}[\text{parent}(k)] \leftarrow \text{tree}[\text{parent}(k)] + \Delta, \quad \text{where } \text{parent}(k) = \lfloor (k-1)/2 \rfloor
\end{equation}
This upward propagation visits exactly $\lceil \log_2 N \rceil = 16$ nodes. Thus, both sampling and updating require strictly $O(\log N)$ steps, reducing execution time by a factor of $\frac{50,000}{16} \approx 3,125\times$ compared to linear scanning.

\paragraph{Floating-Point Precision Drift Mitigation:}
In IEEE 754 32-bit single-precision floating-point arithmetic, adding small priority differences $\Delta \approx 10^{-4}$ to large accumulated sums ($\text{tree}[0] \approx 10^5$) introduces truncation error. Over $10^5$ training steps, cumulative round-off causes the root value to deviate from the actual sum of the leaves by up to $2.4\%$. To eliminate drift:
\begin{itemize}
    \item The priority buffer uses 64-bit double-precision floats (\code{float64}) for tree nodes.
    \item A periodic full-tree re-summation kernel executes every $10,000$ updates, recomputing all internal nodes directly from leaves in a bottom-up sweep in $O(N)$ time (taking only $1.2$~ms).
\end{itemize}

\section{Question 4: High-Availability Failover Architecture and Timing Breakdown}
\textbf{Examiner Query:} \emph{Explain the exact controller resilience architecture implemented in \code{ha_controller_pool.py}, separate the failover timing components, and clarify how it relates to full distributed consensus.}

\paragraph{Exact Implemented Mechanism:}
The prototype implements a \textbf{Health-Checked Active/Standby Multi-Controller Pool}, consisting of one Primary and two Backup controller instances listening on separate ports (OFP 6633/6634/6635, REST 8080/8081/8082).
Failover is structured across four decoupled stages:
\begin{enumerate}
    \item \textbf{Failure Detection Delay ($\le 1.0$~s):} The health prober issues HTTP GET \code{/api/health} requests with a 1.0-second timeout. When the primary process dies or ceases responding, the prober catches a socket timeout or \code{ConnectionRefusedError}.
    \item \textbf{Local Promotion Bookkeeping ($0.001$~ms):} When failover is triggered, \code{_trigger_failover()} updates the pool's in-memory active node index (\code{self.active_index = new_idx}) and appends a telemetry record to \code{self.failover_history}. This operation is strictly local CPU memory pointer reassignment and dictionary bookkeeping in Python, measured accurately at \textbf{0.001~ms} (1.0~$\mu$s).
    \item \textbf{Client HTTP Recovery ($37.96$~ms):} When an external client issues a REST request during failover, \code{execute_request()} catches the broken socket connection to the failed primary, iterates to the designated healthy standby, and retries the HTTP request. This entire detection, redirection, and HTTP response loop completes in \textbf{37.96~ms}.
    \item \textbf{Data-Plane Packet Continuity ($0$ dropped packets):} Open vSwitch switches are provisioned with multi-controller target strings (\code{tcp:127.0.0.1:6633}, \code{tcp:127.0.0.1:6634}, \code{tcp:127.0.0.1:6635}). Southbound OpenFlow connections reconnect asynchronously, while existing TCAM flow table entries maintain line-rate packet forwarding uninterrupted, yielding zero data-plane drops.
\end{enumerate}

\paragraph{Distinction from Distributed Raft Consensus and Production Roadmap:}
To remain conservative and transparent, we explicitly distinguish this pool implementation from full distributed consensus:
\begin{itemize}
    \item \textbf{What is Implemented:} A health-checked active/standby failover pool with client HTTP redirection and sub-millisecond local selection bookkeeping.
    \item \textbf{What is Not Implemented:} The prototype does not include a distributed replicated log, leader election terms, quorum voting RPCs, or split-brain partition resolution (such as Raft or Paxos).
    \item \textbf{Production Carrier Evolution:} In a geographically distributed multi-datacenter deployment, network partitions can isolate controller nodes. A full production implementation would integrate Raft consensus \cite{ongaro2014search} requiring majority quorum ($Q = \lfloor N/2 \rfloor + 1$) to elect leaders, coupled with OpenFlow 1.3 Role Requests (\code{OFPT_ROLE_REQUEST}) and 64-bit monotonically increasing \code{generation_id} counters to ensure switches reject stale commands from deposed leaders.
\end{itemize}

\section{Question 5: Zero-Shot Generalization Limits and Graph Neural Networks}
\textbf{Examiner Query:} \emph{Why can a fixed-vector D3QN agent not generalize zero-shot to arbitrary unseen topologies, and how do Graph Neural Networks (GNNs) solve this via relational inductive biases?}

\paragraph{Dimensionality Lock of Fixed-Vector Representations:}
In our prototype D3QN architecture, the state input is a Euclidean tensor $\mathbf{s} \in \mathbb{R}^{10}$, and the action space is discrete $\mathcal{A} = \{0, 1, \dots, K-1\}$, corresponding to the $K$ candidate paths produced by Yen's $K$-Shortest Paths on the specific trained topology (e.g., 20-switch Fat-Tree Clos).
This imposes two structural bottlenecks:
\begin{enumerate}
    \item \textbf{Input Dimension Incompatibility:} If the network expands to 24 nodes (US Carrier) or 36 network nodes (Fat-Tree $k=4$, comprising 20 switches and 16 hosts), the number of links, congested bottlenecks, and feature dimensions changes. A dense neural network layer $\mathbf{W} \in \mathbb{R}^{h \times 10}$ cannot accept input vectors of differing dimensions $\mathbb{R}^{M}$ ($M \neq 10$) without arbitrary padding or truncation.
    \item \textbf{Permutation Sensitivity:} Dense MLPs treat each input coordinate as an independent semantic dimension. If the node indexing of the topology is permuted ($v_i \leftrightarrow v_j$), the MLP produces entirely different outputs, even though the physical graph topology is completely isomorphic.
\end{enumerate}

\paragraph{Relational Inductive Biases via Graph Neural Networks (GNNs):}
To achieve genuine zero-shot generalization across arbitrary, previously unseen network topologies, the reinforcement learning agent must operate directly over topological graphs $\mathcal{G} = (\mathcal{V}, \mathcal{E})$ using Graph Neural Networks \cite{scarselli2008graph, battaglia2018relational, rusek2019routenet}.

In a Message-Passing Neural Network (MPNN), the network state is defined by node feature vectors $\mathbf{h}_v \in \mathbb{R}^{d_v}$ and directed edge feature vectors $\mathbf{e}_{uv} \in \mathbb{R}^{d_e}$ (representing capacity, instantaneous utilization, queue backlog, and link delay).
At each graph convolution layer $l \in \{1, \dots, L\}$:
\begin{enumerate}
    \item \textbf{Message Generation:} Each edge generates a message from its source and destination node embeddings:
    \begin{equation}
    \mathbf{m}_{uv}^{(l)} = \text{MLP}_{\text{msg}}\left( \left[ \mathbf{h}_u^{(l)}, \, \mathbf{h}_v^{(l)}, \, \mathbf{e}_{uv} \right] \right)
    \end{equation}
    \item \textbf{Permutation-Invariant Aggregation:} Each node aggregates incoming messages from its local neighbors $\mathcal{N}(v)$:
    \begin{equation}
    \mathbf{a}_v^{(l)} = \bigoplus_{u \in \mathcal{N}(v)} \mathbf{m}_{uv}^{(l)}
    \end{equation}
    where $\bigoplus \in \{\sum, \text{mean}, \max\}$ is an associative and commutative aggregation operator guaranteed to be invariant to neighbor ordering.
    \item \textbf{Node State Update:} The node updates its hidden embedding via a recurrent or feedforward cell:
    \begin{equation}
    \mathbf{h}_v^{(l+1)} = \text{GRU}\left( \mathbf{h}_v^{(l)}, \, \mathbf{a}_v^{(l)} \right)
    \end{equation}
\end{enumerate}

\paragraph{Permutation Equivariance and Zero-Shot Transfer Proof:}
Let $\mathbf{P} \in \{0, 1\}^{|\mathcal{V}| \times |\mathcal{V}|}$ be an arbitrary permutation matrix relabeling the graph nodes. Because the aggregation operator $\bigoplus$ is symmetric:
\begin{equation}
\text{GNN}(\mathbf{P} \mathcal{G}) = \mathbf{P} \, \text{GNN}(\mathcal{G})
\end{equation}
The node and link representations are strictly \textbf{permutation equivariant}. To evaluate a candidate path $\pi = (e_1, e_2, \dots, e_m)$, a path readout function aggregates the edge embeddings along the path:
\begin{equation}
Q(\pi) = \text{MLP}_{\text{eval}}\left( \sum_{e \in \pi} \mathbf{e}_{e}^{(L)} \right)
\end{equation}
Because the message passing relies solely on local topological connectivity rather than global matrix dimensions, a theoretical GNN agent trained on a reference topology can be evaluated on networks of arbitrary scale (in contrast to fixed-input MLPs, which require topological feature aggregation as performed in our Fat-Tree D3QN zero-shot transfer evaluation).

\section{System Prerequisites and Dependencies}
The Adaptive SDN Traffic Engineering Platform is engineered to run natively on Linux-based environments (Ubuntu 20.04 LTS, Ubuntu 22.04 LTS, Ubuntu 24.04 LTS, or Debian 11/12).

\subsection{Hardware Requirements \& Reference Deployment Environment}
The reference production deployment was hosted inside a dedicated 64-bit Ubuntu virtual machine running under the VMware hypervisor (see Figure~\ref{fig:vmware_specs}):
\begin{itemize}
    \item \textbf{Virtual Processors}: 4 virtual CPU cores (vCPUs) with hardware virtualization extensions enabled.
    \item \textbf{System Memory (RAM)}: 8.0~GB of dedicated memory (minimum: 4~GB; 8~GB recommended for 20-switch Clos emulations).
    \item \textbf{Disk Storage}: 60.0~GB SCSI virtual disk (minimum: 10~GB free space for dependencies, dataset logs, and model checkpoints).
    \item \textbf{Network Adapter}: NAT virtual adapter with isolated internal loopback for OpenFlow and REST dashboard communication.
\end{itemize}

\subsection{Software Requirements}
\begin{itemize}
    \item \textbf{Operating System}: Linux kernel 5.4 or higher with Open vSwitch kernel module support.
    \item \textbf{Python Environment}: Python 3.9 to Python 3.12 (Python 3.14 compatible).
    \item \textbf{Network Virtualization}: Mininet Version 2.3.0+ and Open vSwitch (OVS) 2.13+.
    \item \textbf{Deep Learning Framework}: PyTorch 2.0+ (CPU or CUDA).
    \item \textbf{SDN Framework}: Ryu SDN Framework 4.34+.
    \item \textbf{Web Browser}: Google Chrome, Chromium, Firefox, or Safari with HTML5 Canvas support.
\end{itemize}

\section{Installation and Environment Initialization}
The platform includes automated launcher scripts that detect the active Python virtual environment without manual path exports.

\subsection{Step-by-Step Installation}
\begin{lstlisting}[language=bash, caption={Platform Environment Setup}]
# 1. Clone repository and navigate to root directory
git clone https://github.com/maher-alqadhi/Reinforcement_Learning_for_Adaptive_Traffic_Engineering_in_an_SDN_Network.git
cd Reinforcement_Learning_for_Adaptive_Traffic_Engineering_in_an_SDN_Network

# 2. Create isolated Python virtual environment
python3 -m venv .venv
source .venv/bin/activate

# 3. Upgrade package installer and install core dependencies
pip install --upgrade pip
pip install -r requirements.txt
\end{lstlisting}

\section{Interactive Web Dashboard User Guide}
The Web Dashboard interface is structured into six functional zones:
\begin{enumerate}
    \item \textbf{Global Navigation Bar}:
    \begin{itemize}
        \item \textit{Fabric Topology Pill}: Displays the active network topology (e.g., Hierarchical Tree, Clos Fat-Tree).
        \item \textit{Model Parameters Badge}: Displays loaded D3QN weights ($26,501$ parameters). Clicking opens the Neural Network Inspector modal.
        \item \textit{Exploration Badge ($\varepsilon$)}: Shows the active exploration rate ($\varepsilon = 0.010$).
        \item \textit{Theme Toggle (Light/Dark)}: Instantly toggles between high-contrast daylight theme and dark mode.
        \item \textit{Telemetry Auto-Refresh}: Pauses or activates automatic 2.5-second telemetry polling.
        \item \textit{Network Settings Button}: Opens the global architecture configuration modal.
    \end{itemize}
    
    \item \textbf{Real-Time KPI Strip}:
    \begin{itemize}
        \item \textit{Fabric Throughput (Mbps)}: Real-time aggregated data plane throughput with active flow count.
        \item \textit{Bottleneck Load (\%)}: Peak link utilization across all network links with status pill (Optimal $<45\%$, Moderate $45$--$75\%$, Congested $>75\%$).
        \item \textit{Latency \& Jitter (ms)}: Average end-to-end path latency, Echo-RTT delay variation, and packet loss percentage.
        \item \textit{Control Plane Rate (msg/s)}: OpenFlow asynchronous message throughput and mean D3QN decision latency.
    \end{itemize}
    
    \item \textbf{Interactive OpenFlow 1.3 Canvas Fabric}:
    \begin{itemize}
        \item \textit{Pan \& Zoom Controls}: Zoom In ($+$), Zoom Out ($-$), Reset Zoom ($100\%$), or use mouse wheel zoom centered at cursor position.
        \item \textit{Node Selection}: Click any switch node to designate it as the Source switch (green halo) or Destination switch (pink halo).
        \item \textit{Utilization Badges}: Real-time link percentage badges displaying link saturation levels.
        \item \textit{Severed Link Overlay}: Rendered as dashed red lines with a central \texttt{[SEVERED]} badge during simulated link failures.
    \end{itemize}
    
    \item \textbf{Interactive Route Predictor \& Decision Explainer}:
    \begin{itemize}
        \item \textit{Source \& Destination Selectors}: Dropdowns allowing instant selection of ingress and egress edge switches.
        \item \textit{Demand Slider}: Adjusts simulated flow bandwidth demand between 5~Mbps and 95~Mbps.
        \item \textit{Predict Route Button}: Dispatches an asynchronous request to \texttt{/api/model\_predict}, executing D3QN inference ($<2.5\text{ ms}$).
        \item \textit{Apply Flow to Fabric Button}: Dynamically injects the selected flow into the active state manager, updating link loads and flow tables in real-time.
        \item \textit{Softmax Q-Value Table}: Renders all candidate path alternatives, action indices $a^*$, Q-softmax choice probabilities, projected bottlenecks, and path latencies.
    \end{itemize}
    
    \item \textbf{Algorithm Tournament Arena}:
    \begin{itemize}
        \item \textit{Protocol Checklist Chips}: Toggle D3QN, OSPF, ECMP, WSP, LLR, or Dijkstra SPF for comparative head-to-head simulation.
        \item \textit{Workload Pattern}: Select between Poisson, Core Congestion Jamming, or Asymmetric Burst Shockwave.
        \item \textit{Plot View Tabs}: Switch seamlessly between All-in-One Triad, Metric Deltas (Bar), Delay Trajectory (Timeline), 6D Quality Radar, Latency CDF (Tail SLA), and Load Scaling Curves.
    \end{itemize}
    
    \item \textbf{Chaos Engineering Toolbar}:
    \begin{itemize}
        \item \textit{Sever Link}: Simulates a physical fiber cut on a candidate core or aggregation trunk link.
        \item \textit{Brownout}: Degrades link capacity by 90\% with an artificial latency penalty.
        \item \textit{Burst (+50M)}: Injects an instant +50~Mbps traffic surge to stress the active routing path.
        \item \textit{Restore Links}: Restores all severed or degraded links to nominal operating status.
        \item \textit{Flush Flows}: Flushes all dynamic flow table entries to baseline idle state.
    \end{itemize}
\end{enumerate}

\section{Mininet CLI Operations and OVS Diagnostics}
When running interactive emulations, the Mininet command-line interface provides real-time control:

\begin{lstlisting}[language=bash, caption={Interactive Mininet CLI Emulation Workflow}]
# Launch Mininet with Fat-Tree Clos topology
sudo mn --custom topology/mininet_topo.py --topo fattree --controller=remote,ip=127.0.0.1,port=6633 --switch ovsk,protocols=OpenFlow13

# Inside the Mininet CLI:
mininet> pingall             # Verify full Layer 2 and Layer 3 reachability
mininet> h1 ping -c 5 h16    # Measure end-to-end ping RTT across pod boundaries
mininet> iperf h1 h16        # Generate TCP bandwidth stream between edge hosts
mininet> link s1 s5 down     # Simulate physical link failure between core and agg
\end{lstlisting}

\subsection{Reproducible Packet-Level Mininet Experiment}
\label{app:mininet_protocol}
The scripted experiment is preferred to ad-hoc CLI measurements because it records randomized condition order, raw command output, code hashes, and environment versions. It must be run on a Linux host with Mininet, Open vSwitch, iperf (version 2), and the controller virtual environment installed. It requires root privileges for network namespaces:
\begin{lstlisting}[language=bash, caption={Executing the 120-Trial Factorial Packet Experiment}]
cd EC499tests
sudo ./run_mininet_experiment.sh --matrix --replicates 10
./run_mininet_analysis.sh
\end{lstlisting}
The first command produces 120 randomized trials (2 topologies $\times$ 3 policies $\times$ 2 protocols $\times$ 10 replicates) and writes every raw artifact under \code{logs/mininet\_trials/}. The second command creates summary statistics and a figure only if successful measured trials exist; it deliberately fails rather than fabricate absent data. Before citing a packet-level result, preserve the raw run directory, \code{mininet\_measured\_trials.json}, \code{mininet\_measured\_analysis.json}, and the generated figure in the submission archive.

\subsection{Configuring Shadow Reservations and TCAM Allocation}
Operators can tune active shadow reservation parameters and TCAM allocation timeouts directly in \texttt{config.py} or via environment variables:
\begin{itemize}
    \item \texttt{SHADOW\_DECAY\_HALF\_LIFE}: Half-life decay duration in seconds (default: $1.5\text{ s}$). Controls how fast temporary flow reservations decay between OpenFlow telemetry polling cycles.
    \item \texttt{ELEPHANT\_FLOW\_THRESHOLD\_MBPS}: Rate threshold for elephant flow classification (default: $5.0\text{ Mbps}$). Flows exceeding this rate receive dedicated 5-tuple TCAM rules.
    \item \texttt{MICE\_IDLE\_TIMEOUT}: Idle timeout for wildcard aggregated mice flows (default: $15\text{ s}$).
    \item \texttt{ELEPHANT\_IDLE\_TIMEOUT}: Idle timeout for pinned elephant flows (default: $60\text{ s}$).
\end{itemize}
